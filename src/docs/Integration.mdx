# Integration

The widget turns a small mission-state input into a consistent status and control surface. A local provider is enough for an isolated example; a controlled provider lets an application own state and command handling.

## Start with local state

The example below uses the real public components and is compiled by the project’s TypeScript build. Mission names, timer icons, and control sets are derived from configuration rather than supplied independently.

## Choose the state owner

<div className="widget-docs-table" role="region" aria-label="State ownership modes" tabIndex={0}>
<table>
  <thead><tr><th>Mode</th><th>Use when</th><th>Contract</th></tr></thead>
  <tbody>
    <tr><td>Local</td><td>An example or a containing component does not need to drive every update.</td><td>Pass <code>initialState</code>. It is read on mount. An optional <code>onStateChange</code> observes updates.</td></tr>
    <tr><td>Controlled</td><td>The application owns the current mission state.</td><td>Pass <code>state</code> and <code>onStateChange</code>. Store the proposed next state and pass it back.</td></tr>
  </tbody>
</table>

The TypeScript props require one ownership mode. Do not pass `state` and `initialState` together. In controlled mode, the component does not silently keep a second authoritative copy of application state.

<Source dark language="tsx" code={`import { useState } from 'react';
import {
  AutonomyWidget,
  AutonomyWidgetProvider,
  type AutonomyWidgetActionEvent,
  type AutonomyWidgetStateInput,
} from '../components/AutonomyWidget';

function MissionPanel({ onAction }: {
  onAction: (event: AutonomyWidgetActionEvent) => void;
}) {
  const [state, setState] = useState<AutonomyWidgetStateInput>({
    action: 'waypoint-mission',
    time: 90,
  });

  return (
    <AutonomyWidgetProvider
      state={state}
      onStateChange={setState}
      onAction={onAction}>
      <AutonomyWidget />
    </AutonomyWidgetProvider>
  );
}`} />

## Keep inputs separate from presentation

`createAutonomyWidgetState(input)` resolves the mission and derives its display fields synchronously. The same resolver is used by the provider, so consumers do not need to repeat display strings or wait for an effect to populate the first frame.

`actionName`, `timerIcon`, and `buttons` are resolved output. Storybook hides them from Controls because editing those values independently would create a misleading mission state. Prefer an active action plus `isPaused` for the interactive flow; retained paused-state fixtures remain available for review.

## Connect intent to the application

The provider exposes two callback seams:

- `onAction` receives a mission action event with `type: 'mission-action'`, the current `action`, and the selected control `id`. A configured button callback also runs when present.
- `onOrbitProgressChange` observes the orbit percentage emitted after the shared state update is requested.

Pause, resume, and expansion produce state updates through `onStateChange`. They do not pretend that an external command has been acknowledged.

An application can route these callbacks to its own transport. It must also own pending, acknowledged, rejected, and telemetry-reconciled states. No network request or drone command is sent by this repository.

## Update a mission deliberately

A child can use `useAutonomyWidget()` to read `{ state, setState }`. The hook throws a descriptive error outside its provider.

<Source dark language="tsx" code={`import { useAutonomyWidget } from '../components/AutonomyWidget';

function ReturnToDockButton() {
  const { setState } = useAutonomyWidget();

  function handleClick() {
    setState(previous => ({
      ...previous,
      action: 'returning-to-dock',
      isPaused: false,
      expanded: false,
    }));
  }

  return <button onClick={handleClick}>Return to dock</button>;
}`} />

Changing the action replaces the derived mission presentation. The countdown restarts when `time` changes. A mission transition with the same duration therefore needs an explicit reset policy in the host application.

## Timer and orbit ownership

The timer owns remaining time locally. A running countdown ticks once per second; pause preserves the value. A normal timer starts with text, then changes to the mission icon after its reading period. `condensed` shows the icon immediately. The standalone Timer’s `progress` override changes the ring independently of countdown text.

The widget owns orbit progress through context. The standalone OrbitSlider also supports local and controlled usage for consumers outside the widget. Its two native buttons adjust bounded values; the track is a reference display, not a draggable range input.

Countdown timing is a local UI mechanism. Authoritative mission time, device synchronization, and command reconciliation remain application responsibilities.
