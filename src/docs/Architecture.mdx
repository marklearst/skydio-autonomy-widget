# One widget. Two ways to own state.

Configuration decides what a mission looks like. State decides which mission is happening. The widget renders that combination and sends user intent back to its owner.

<ArchitectureDiagram />

## Drive it from the outside

This example is a small host application around the real widget. Change a mission in the host, then pause or expand inside the widget. The state readout and event history make both directions visible.

<ExternalControlExample />

The host controls are local demonstration inputs. A real application can map API responses, a store, or device events into the same React state. The widget does not fetch data or connect to a drone itself.

## Start standalone, keep the same component

For an isolated instance, pass `initialState` to `AutonomyWidgetProvider`. It reads the input once and owns subsequent UI state locally. With no input at all, it starts a 90-second waypoint mission.

<Source dark language="tsx" code={integrationSource} />

Import `src/styles/theme.css` once at the application entry. The widget needs its provider and stylesheet, but it has no dependency on Storybook or a network service to run. This is source in this repository, not an installed public widget package.

Each provider isolates its mission state. Give independent widgets separate providers. Widgets under the same provider share mission inputs; each Timer still owns its own local countdown.

For application-owned state, pass `state` and `onStateChange` instead. The owner decides whether to accept each proposed state and supplies the accepted value on the next render. Do not combine `state` and `initialState`.

<Source dark language="tsx" code={controlledSource} />

This is the compiled adapter used by the live host example above. Its caller supplies `state` and callback implementations. The example keeps state in React; a consuming application can connect its own store or API adapter at that boundary.

`AutonomyWidget` takes no direct mission props. Its nearest provider is the state boundary. `useAutonomyWidget()` gives descendants access to `state`, `setState`, and the configured callbacks; calling it outside a provider throws an error.

## Configuration is the mission vocabulary

`AutonomyWidget.configs.ts` defines `ACTION_CONFIGS`, a typed catalog keyed by `ActionType`. `createAutonomyWidgetState(input)` looks up `action` and derives `actionName`, `timerIcon`, and `buttons` synchronously. The renderer selects paused labels and controls using `isPaused`.

<MissionConfigExplorer />

Changing the selected entry above reads a different object from the real file. It does not create a second catalog or edit configuration at runtime.

This catalog is a build-time extension point. Add a new mission to the `ActionType` union and its configuration entry, use an existing icon mapping and Button variant, then cover its active and paused states. A new control kind also requires renderer support. `primaryButton` and `iconRotation` are retained metadata and do not drive the current renderer.

Prefer an active mission plus `isPaused` for a new integration. The three paused catalog keys are retained fixtures, not a requirement to model pause as another mission.

## The complete state and callback contract

<table>
  <thead><tr><th scope="col">State input</th><th scope="col">Contract</th></tr></thead>
  <tbody>
    <tr><td><code>action</code></td><td>Required mission key. Unknown runtime values normalize to idle.</td></tr>
    <tr><td><code>time</code></td><td>Required duration in seconds, normalized to a whole number from 0 to 3,599. Non-finite values become 0.</td></tr>
    <tr><td><code>isPaused</code></td><td>Optional, defaults to false. Preserves remaining countdown time and selects paused presentation.</td></tr>
    <tr><td><code>expanded</code></td><td>Optional, defaults to false. Reveals available secondary actions at viewports of at least 600px.</td></tr>
    <tr><td><code>orbitProgress</code></td><td>Optional percentage, normalized to 0–100. Omitted or non-finite input becomes 50.</td></tr>
  </tbody>
</table>

`actionName`, `timerIcon`, and `buttons` are resolved output. Compatibility input accepts them, but the resolver overwrites them; author the mission input rather than duplicating presentation fields.

The input `action: 'waypoint-mission'` selects a mission. The output `id: 'next'` identifies a button the operator pressed. Those are separate concepts: a Next click emits intent; it does not automatically advance a real mission.

## Connect an application deliberately

An incoming command is handled by the host. The host can map that command or an API response to a new `state.action`, duration, and presentation state. There is no imperative `dispatch(command)` endpoint on the widget; its integration API is React state in and callbacks out.

1. Map application data into `AutonomyWidgetStateInput` and supply it as controlled `state`.
2. Decide which UI state proposals to accept through `onStateChange`.
3. Route `onAction` and orbit callbacks into the application’s command layer.
4. Own pending, acknowledged, rejected, and telemetry-reconciled command states in the application.

`time` is a duration input, not authoritative remaining time. Timer ticks are local; changing only the mission with the same duration preserves its countdown. A new mission that needs a fresh countdown at the same duration requires an explicit reset/remount policy in the host.
